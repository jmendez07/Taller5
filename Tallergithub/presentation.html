Pitch del acelerador

Objetivo del Taller

Diseñar capacidades escalables de IA para equipos de datos: estándares, prompts, revisiones y agentes que puedan reutilizarse más allá de una persona o proyecto.

Rol del Participante

Actuar como promotor de adopción: traduce prácticas individuales en activos compartidos para su equipo.

Producto de Salida

Un kit de equipo para Copilot con instrucciones, prompts, lista de revisión y diseño de un acelerador especializado.

La meta no es aprender más comandos. La meta es que el equipo trabaje con una forma común, repetible y gobernada de usar IA.

El Problema que Queremos Resolver

Uso Individual

  • Cada persona pregunta distinto
  • Los estándares viven en la cabeza de expertos
  • Los prompts buenos se pierden en conversaciones
  • La calidad depende de quien use la herramienta

Capacidad de Equipo

  • Instrucciones comunes y versionadas
  • Prompts reutilizables por flujo de trabajo
  • Revisión asistida con criterios consistentes
  • Agentes diseñados con límites claros
Principio de diseño: si una práctica con Copilot funciona dos veces, debe poder documentarse, versionarse y compartirse.

Ejemplo: Custom Instruction en Acción

Contexto

Trabajamos con arquitectura medallón, notebooks, pipelines y consultas analíticas.

Estándares Clave

  • Sin SELECT *
  • Supuestos explícitos
  • Salida con recomendaciones verificables
  • Alertas sobre datos sensibles

Práctica 1: Estándares de Uso de Copilot

Trabajo en grupos

Construir la instrucción base

Cada grupo define cómo Copilot debe comportarse cuando ayude en tareas de datos: tono, estándares técnicos, límites y formato de salida.

Criterio de calidad

Debe ser accionable

Una buena instrucción no dice “hazlo bien”. Define reglas verificables: nombres, patrones, pruebas, documentación y restricciones.

Actúa como asistente senior para equipos de datos. Cuando generes código SQL, PySpark o Python: - Explica supuestos antes de proponer cambios. - Evita SELECT * y filtros no sargables. - Prioriza legibilidad, trazabilidad y manejo explícito de errores. - No inventes columnas, tablas, rutas ni credenciales. - Señala riesgos de datos sensibles y pide validación humana cuando aplique.

Plantilla: Custom Instructions del Equipo

1. RolAsistente esperado: ingeniero de datos, analista, arquitecto, revisor o documentador.
2. ContextoPlataformas, lenguajes, repositorios, arquitectura de datos y convenciones locales.
3. EstándaresReglas de SQL, Python, notebooks, pruebas, documentación y naming.
4. RestriccionesDatos sensibles, credenciales, ambientes productivos y acciones no permitidas.
5. Formato de salidaTablas, listas de verificación, diferencias, fragmentos, documentación o explicación paso a paso.
6. ValidaciónQué pruebas, revisiones o aprobaciones deben ocurrir antes de adoptar el resultado.

Dónde Viven las Instrucciones en GitHub

Las Custom Instructions no son solo texto: son archivos versionados dentro del repositorio que Copilot lee automáticamente.

ArchivoAlcanceCuándo usarlo
.github/copilot-instructions.mdTodo el repositorioEstándares globales del equipo: tono, reglas, restricciones y formato.
.instructions.mdCarpeta actual y subcarpetasReglas específicas por módulo, capa o componente.
.github/prompts/*.prompt.mdInvocable desde el chatPrompts reutilizables que cualquier miembro puede ejecutar directamente.
Estos archivos se versionan con Git como cualquier otro activo del proyecto. Cambios pasan por pull request y revisión.

Librerías de Prompts

¿Qué es?

Una colección organizada de instrucciones, preguntas y plantillas que un equipo reutiliza para obtener resultados consistentes.

Reutilización

En lugar de escribir prompts desde cero, los equipos reutilizan plantillas probadas que garantizan calidad y consistencia.

Cómo Diseñar una Librería de Prompts

CategoríaUso TípicoEjemplo de Prompt
SQL y DatosOptimización, validación, explicación de consultasRevisa esta consulta y detecta riesgos de rendimiento y calidad de datos.
PySpark / PythonRefactor, errores, pruebas, patrones reutilizablesPropón una versión más legible y testeable de esta transformación.
DocumentaciónREADME, runbooks, diccionarios de datosGenera documentación operacional con supuestos, entradas, salidas y riesgos.
Calidad y GobiernoControles, linaje, privacidad, cumplimientoEvalúa si este flujo maneja datos sensibles y qué controles faltan.
Cada prompt debe tener dueño, versión, caso de uso, entradas esperadas, formato de salida y criterio de aceptación.

Archivos .prompt.md: Prompts como Código

Estructura del archivo

.github/prompts/sql-review.prompt.md --- mode: agent description: Revisa consultas SQL para rendimiento --- Actúa como arquitecto de datos senior. Revisa la consulta adjunta e identifica: 1. Problemas de rendimiento 2. Riesgos de calidad 3. Recomendaciones con severidad Contexto: {{input}}

Ventajas clave

  • Se invocan directo desde Copilot Chat
  • Se versionan con Git (historial y blame)
  • Se comparten al clonar el repositorio
  • Soportan variables y contexto dinámico
  • Cualquier miembro los ejecuta sin configuración
Un archivo .prompt.md convierte una buena práctica individual en una capacidad compartida del equipo desde el primer commit.

Práctica 2: Crear Prompt Cards

Artefacto

Prompt Card

  • Nombre del prompt
  • Problema que resuelve
  • Contexto requerido
  • Formato de respuesta esperado
  • Criterios de calidad
Reto

Crear 3 prompts reutilizables

Uno para SQL, uno para revisión o debugging y uno para documentación. Deben poder usarse por otro equipo sin explicación adicional.

Nombre: Revisor de SQL para rendimiento Objetivo: detectar problemas de costo, filtros, uniones y columnas innecesarias. Entrada: consulta SQL + motor/plataforma + objetivo de negocio. Salida: tabla con hallazgo, severidad, explicación y recomendación. Criterio: no inventar índices, tablas ni columnas; pedir contexto si falta.

Antipatrones Comunes con Copilot

Errores frecuentes

  • Prompts vagos: "hazlo mejor" sin criterio definido
  • Aceptar respuestas sin validar contra datos reales
  • Asumir que Copilot conoce el esquema o contexto interno
  • Instrucciones contradictorias entre archivos
  • Copiar código generado sin entender supuestos

Cómo evitarlos

  • Definir criterios verificables, no adjetivos
  • Siempre validar con evidencia: pruebas, datos, revisión
  • Dar contexto explícito: plataforma, tablas, restricciones
  • Mantener una sola fuente de verdad por alcance
  • Tratar la respuesta como borrador, no como solución final
Regla de oro: si no puedes explicar por qué la respuesta de Copilot es correcta, no la uses.

Revisión de código asistida por IA

Ventajas

  • Análisis rápido y exhaustivo
  • Primer filtro automatizado
  • Criterios consistentes

Sinergia

Copilot identifica problemas frecuentes. Las personas revisan impacto, contexto, arquitectura y decisiones de negocio.

Práctica 3: Revisión de consulta SQL

Prompt de Revisión

Actúa como Arquitecto de Datos Senior. Revisa esta consulta SQL e identifica: 1. Problemas de rendimiento. 2. Riesgos de calidad o seguridad. 3. Buenas prácticas incumplidas. 4. Recomendaciones de mejora con severidad.

Código a Revisar

SELECT * FROM transacciones t WHERE YEAR(fecha_transaccion) = 2025

Mejoras Esperadas

  • Columnas explícitas
  • Filtro por rango de fechas
  • Riesgos y supuestos documentados
  • Índices o particiones a validar

Lista de verificación: revisión de código asistida

Calidad Técnica

  • Legibilidad y nombres claros
  • Complejidad innecesaria
  • Manejo de errores y casos borde
  • Pruebas o validaciones mínimas

Datos y Seguridad

  • Datos sensibles expuestos
  • Credenciales o secretos en código
  • Supuestos no documentados
  • Permisos y ambientes productivos

Rendimiento

  • Filtros eficientes
  • Columnas explícitas
  • Uniones controladas
  • Particionamiento y volumen estimado

Decisión Humana

  • Qué aprobar
  • Qué corregir
  • Qué escalar
  • Qué evidencia falta

Diseño de Agentes Especializados

Un agente no es un prompt largo. Es una capacidad diseñada para una tarea repetible, con rol, contexto, entradas, salidas, límites y criterios de validación.

Agente de SQL

Optimiza consultas, explica planes, detecta riesgos y propone alternativas.

Revisor de Código

Evalúa calidad, seguridad, mantenibilidad y cobertura antes del pull request.

Generador de Documentación

Produce README, runbooks, diccionarios de datos y notas de operación.

Canvas del Acelerador

Usuario Objetivo¿Quién lo usará y en qué momento del flujo de trabajo?
Problema Repetible¿Qué tarea consume tiempo, genera retrabajo o depende de expertos?
EntradasCódigo, consulta, notebook, tabla, error, documentación o contexto funcional.
InstruccionesRol, reglas, estándares, restricciones y formato esperado.
SalidaRecomendación, diferencia, lista de verificación, reporte, documentación o plan de acción.
Control HumanoQué debe revisar una persona antes de aceptar el resultado.

Práctica 4: Diseñar un Acelerador

Opciones

Elige un caso

  • Agente de SQL
  • Revisor de Código
  • Generador de Documentación
  • Asistente de Onboarding
  • Analista de Calidad de Datos
Entrega

Diseño mínimo viable

Completar el canvas, escribir el prompt principal, definir límites y simular una interacción con una entrada realista.

Un buen acelerador debe ser específico. “Ayudar con datos” es demasiado amplio; “revisar consultas SQL de reporting antes del merge” sí es operable.

De Canvas a Implementación

El acelerador diseñado en el canvas se materializa como un archivo ejecutable en el repositorio del equipo.

Ruta de implementación

  • Canvas completado en el taller
  • Instrucciones base en .github/copilot-instructions.md
  • Prompt invocable en .github/prompts/mi-agente.prompt.md
  • Validación con caso real del equipo
  • Pull request para revisión y aprobación

Evolución progresiva

  • v0: prompt simple con instrucciones fijas
  • v1: prompt con variables y contexto dinámico
  • v2: agente con herramientas (MCP) si la complejidad lo requiere
  • v3: flujo multi-agente con orquestación
No todo necesita ser un agente complejo. La mayoría de aceleradores para equipos de datos empiezan como un buen .prompt.md con instrucciones claras.

Gobernabilidad de Sistemas Agénticos

Gobernabilidad es la capacidad de controlar, limitar y auditar lo que un agente puede hacer, sobre qué datos opera y quién autoriza sus acciones.

Controles esenciales

  • Alcance definido: qué tareas puede y no puede hacer
  • Datos permitidos vs. restringidos (PII, secretos, producción)
  • Aprobación humana obligatoria antes de cambios críticos
  • Versionamiento de instrucciones y prompts en Git
  • Política de "no merge sin revisión documentada"

Cómo implementarlo

  • Restricciones en .github/copilot-instructions.md
  • Límites explícitos en cada .prompt.md
  • Pull requests como evidencia de validación humana
  • Roles claros: quién aprueba, quién opera, quién audita
  • Registro de cambios asistidos por IA en commits
En una organización regulada, la pregunta no es "¿funciona?" sino "¿puedo demostrar que fue controlado, autorizado y validado?"

Observabilidad en Agentes de IA

Observabilidad es la capacidad de entender qué hizo el agente, por qué lo hizo, cuánto tardó y qué impacto tuvo, sin necesidad de reproducir la sesión.

Trazas

  • Entrada del usuario
  • Instrucciones aplicadas
  • Herramientas invocadas
  • Respuesta generada
  • Decisión humana final

Métricas

  • Tasa de aceptación de respuestas
  • Prompts más y menos usados
  • Tiempo ahorrado por tarea
  • Errores detectados por revisión
  • Cobertura del equipo

Señales de alerta

  • Agente usado fuera de contexto
  • Respuestas aceptadas sin revisión
  • Prompts sin dueño ni versión
  • Cambios productivos sin aprobación
  • Caída en tasa de uso del equipo
La observabilidad convierte al agente en un sistema operado, no en una caja negra. Sin trazas no hay mejora continua.

Evaluación de Sistemas Agénticos

Evaluación es el proceso de medir si el agente cumple su propósito: produce respuestas correctas, seguras, útiles y dentro de los límites definidos.

Qué evaluar

DimensiónPregunta clave
Correctitud¿La respuesta es técnicamente correcta?
Relevancia¿Resuelve el problema planteado?
Seguridad¿Respeta límites de datos y acciones?
Consistencia¿Produce resultados similares ante entradas similares?
Utilidad¿Reduce tiempo o mejora calidad?

Cómo evaluar

  • Casos de prueba con entrada y salida esperada
  • Revisión entre pares de respuestas generadas
  • Comparación antes/después en tareas reales
  • Registro de hallazgos falsos positivos y negativos
  • Iteración: ajustar instrucciones según resultados
Un agente que no se evalúa regularmente se degrada. La evaluación es el motor de mejora continua.
